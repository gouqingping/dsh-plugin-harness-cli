# 术语表

> 统一口径，避免同一件事在不同人嘴里有不同叫法。**遇到看不懂的词先查这里。**
> 第三列「业务含义」是**标准口径**；第四列是容易混淆的地方。按主题分组，组内不排序。

## 1. 体系与文件

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| Harness | 工程化约束 / 协作骨架 | 把「项目该怎么协作」写成文件，并让机器检查是否遵守 | 不是某个框架或库，也不是 AI 模型 |
| 四件套 | 入口 / 环境 / 范围 / 状态 | 四类必须存在的文件：入口地图、环境初始化、功能清单、进度日志 | 常被误认为「四个文档」，其实还包括门禁脚本 |
| 入口地图 | `AGENTS.md` | 新人/新会话的第一站：项目定位、目录地图、命令、约定、工作流、禁止事项、完成定义、深入阅读 | 不是手册；超过建议行数要拆到 `docs/` |
| 结构文件 | structural | 由配置与模板生成的产物（入口地图、门禁脚本、CI 骨架、版本说明等），可按显式要求重生成 | 与「状态文件」相对；重生成不会丢信息 |
| 状态文件 | state | 只能增量维护的文件：功能清单、进度日志、任务日志、任务队列 | 即使显式要求覆盖也不覆盖（需连状态一起覆盖） |
| 生成物 | artifacts | 一次生成落在目标仓库里的全部文件与目录 | 常在客户仓库里，不在工具目录里 |
| 配置入口 | `harness-cli.json` | 唯一的可调整入口：项目信息、路径、命令、目录、约定、开关 | 旧文件名（`harness-pro.json` / `common-agent.json`）仍可读，但会提示改名 |

## 2. 范围与状态

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| 功能（范围条目） | feature / `F-001` | 范围清单里的一条「要做什么」，含验收标准与证据 | 不是「任务」；一个功能可以拆成多个任务页 |
| 验收标准 | acceptance | 一条一句、可机械核对的「怎么算做到了」 | 不是需求描述；不能写成「体验良好」 |
| 证据 | evidence | 完成时留下的可复核凭据（命令 + 结果） | 不是「我觉得做完了」；空证据的完成会被判失败 |
| 功能状态 | status | 未开始 / 进行中 / 已完成 / 被阻塞 | 「已完成」是一种状态，不是一句结论 |
| 并行上限 | `wipLimit` | 同时处于「进行中」的功能数量上限，默认 1 | 与「认领数量上限」是同一个数，不是两套 |
| 阻塞 | blocked | 因外部原因暂时不能推进 | 与「进行中但很慢」不同：阻塞必须写原因 |
| 任务 | task / 任务页 | 一次具体推进：一页 + 四份文档 + 一份认领 | 不要与「功能」混用 |

## 3. 进度与文档

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| 任务页 | progress page | `prototype/<任务>/progress.html`：五段式页面（领域 / 契约 / 用例 / 规划 / 记录） | 不是文档正文；它承载状态与百分比 |
| UI 设计稿 | `ui/index.html` | 任务目录下的 antd v5 静态设计稿 + 设计说明 | 不是实现代码；也不放进度百分比 |
| 方案页 | `plan.html` | 任务目标 / 方案 / 页面设计 / 流程交互 / 风险 / 验收 + 确认记录 | 不是任务页；确认前不许开工 |
| 进度写入口 | `progress` | 唯一改写步骤与状态、自动追加记录并同步总览的命令 | 不是手改 HTML；手改会触发 P9/P11 |
| 复盘 | review / `review.md` | Agent 核对文档与任务页并记录文档指纹，作为确认前提 | 不是最终确认；确认由人执行 |
| 文档指纹 | docs hash | 四份文档内容的 sha1，确认时写入 `plan.html` | 改文档后指纹变，确认失效 |
| 总览页 | index page | `prototype/progress.html`：所有进行中 / 待验收任务的汇总 | 手改会判「过期」；由汇总命令生成 |
| 进度日志 | `claude-progress.md` | 给下一个会话看：本次目标、已完成、验证结果、问题、下一步行动 | 不是页面；不写百分比 |
| 任务日志 | `docs/current.md` | 按任务记录：范围、落地内容、验证命令与结果、未完成项 | 与进度日志职责不同，两者都要维护 |
| 总进度 | total progress | 各步骤百分比的等权平均，自动汇总 | **不手填**；手填且与汇总不一致会失败 |
| 进度记录 | log entry | 每次变化追加一条：时间 + 变化后的总进度 + 说明 | 只追加不删；末条必须等于当前汇总 |
| 规范文档 | `docs/specs/` | 每个任务四份：提案、契约、设计、任务规划 | 与任务页同源但不同物；交付评审看文档 |
| 提案 | proposal | 为什么做、范围与非目标、验收 | 不是需求评审记录 |
| 契约 | spec / `S-01` | SDD 的核心：一条行为的输入、输出、错误语义、验收标准 | 不是接口文档的「接口」；没有错误语义不算契约 |
| 任务规划 | tasks / 1..N | 编号连续的步骤，每步绑定一条契约，可人工增删 | 与页面步骤必须一一对应 |
| 同步 | `--sync` | 用任务页重新汇总总览页 | 不是「保存」；它只改总览 |

## 4. 拆分方法

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| DDD | 领域驱动设计 | 先划边界：限界上下文、统一语言、聚合、不变量 | 不是分层架构；重点是边界与语言 |
| 限界上下文 | bounded context | 这个任务属于哪个业务边界；边界外的概念不进来 | 不是「模块名」或「目录名」 |
| 统一语言 | ubiquitous language | 本任务内每个术语的一句话定义，≥3 条 | 不是术语表全文；只收本任务用到的 |
| 聚合 / 实体 | aggregate / entity | 改动落在哪个聚合根上，它守什么规则 | 不是数据表 |
| 不变量 | invariant | 任何时刻都必须成立的一句话 | 不是「最好这样」；必须是硬约束 |
| SDD | 规范驱动开发 | 把需求写成 AI 能精准执行的契约 | 不是写更长的需求文档 |
| TDD | 测试驱动开发 | 先写测试（红）→ 实现到通过（绿） | 不是「写完再补测试」 |
| 用例红/绿 | red / green | 红 = 测试已写好尚未通过；绿 = 已通过 | 红不是「失败」，是「还没实现」 |

## 5. 并行协作

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| 认领 | claim | 声明「这个任务我在做、我会改这些路径」，写进仓库 | 不是口头分工；口头分工不算 |
| 认领人 | owner | 做这件事的人 / 会话 / Agent 标识 | 不是「负责人」；负责人是交付角色 |
| 范围 | scope | 认领人承诺会改的路径（前缀语义，可多条） | 空范围无法判断冲突，只给警告 |
| 心跳 | heartbeat | 长任务定期更新时间，表示「还活着」 | 不是进度更新；心跳不改进度 |
| 心跳超时 | TTL | 超过配置时长没心跳 → 只警告「可能是死掉的会话」 | 不会自动删除；需人确认后清理 |
| 释放 | release | 收工后删除认领 | 不是「完成」；完成还要推进功能状态与记录 |

## 6. 检查与集成

| 术语 | 英文/别名 | 业务含义（标准口径） | 容易混淆的地方 |
|---|---|---|---|
| 校验 | `check` | 只读检查配置与流程证据是否合规 | 不改文件；修复靠生成命令或人 |
| 严格校验 | `--strict` | 警告也当失败 | 不是「更慢的校验」 |
| 门禁 | gate / `gate.sh` | 一条命令串起 lint → 测试 → 并行上限 + 认领 | 与「校验」不同：门禁是交付前的整链 |
| 自检 | doctor | 检查工具与环境本身（7 项） | 不是项目校验；自检失败先修环境 |
| 风格门禁 | style | 代码风格与提交信息判定（需 python3） | 与项目校验分工不同，退出码语义一致 |
| 退出码 | exit code | 0 通过 / 1 有违规 / 2 工具或用法有错 | 2 不是「更严重的违规」，而是「工具坏了」 |
| 开关 | preset | 可选能力的启用开关（当前：任务页） | 关闭不等于删除已生成文件 |
| 工具 / 命令 | tools / commands | 平台集成后的调用入口：11 个工具 + 10 条斜杠命令；`/harness-cli-help` 一次看全 | 与命令行子命令一一对应，规则完全相同 |
| 业务 wiki | `wiki` / `/harness-cli-wiki` | 从仓库文件生成 `docs/wiki/`（13 篇），已存在则更新受管区块 | 区块外的人工内容不会被覆盖；冲突需确认 |

## 7. 一表记住最容易被问的三个词

| 被问到 | 一句话回答 |
|---|---|
| 「这套系统是什么？」 | 把协作规范变成可生成、可校验的文件。 |
| 「规范文档放哪、进度放哪？」 | 文档进 `docs/specs/`，状态与进度进 `prototype/`。 |
| 「怎么才算做完？」 | 功能有证据 + 页面步骤 100% + 用例全绿 + 门禁全绿 + 验收清单过。 |
