# 业务规范与口径

> 读者：实施与业务人员**上手前请通读一遍**。出现争议以本篇口径为准。
> 本篇解决「大家说的不是同一件事」：对象怎么编号、字段是什么意思、哪些说法最容易混、日常要守什么规矩。

## 1. 对象与编号规则

| 对象 | 编号/命名 | 规则 | 出现在哪 |
|---|---|---|---|
| 功能（范围） | `F-001`、`F-002`… | 三位以上数字，仓库内唯一 | 功能清单 |
| 契约 | `S-01`、`S-02`… | 两位以上数字，页内唯一；被规划与用例引用 | 任务页契约表、`spec.md` |
| 测试用例 | `T-01`、`T-02`… | 两位以上数字，页内唯一；必须挂一条契约 | 任务页用例段 |
| 规划步骤 | `1`、`2`…`N` | 从 1 连续，不许断档；可按人工调整增删 | 任务页步骤、`tasks.md` |
| 任务 | 字母 / 数字 / 中文 / 中划线 / 下划线 | 例如 `login-flow`、`登录页面`；不能有空格或斜杠；同时是页面与文档目录名 | `prototype/<任务>/`、`docs/specs/<任务>/` |
| 认领文件 | `<功能编号>.json` | 与功能编号一致，例如 `F-003.json` | `docs/claims/` |
| 版本 | 语义化版本 | 版本说明文件名为 `v<版本>.md` | `_VERSIONS/` |

**编号三条铁律**：① 已发布的编号不改号，改内容；② 编号不复用（删掉的功能编号不再给新功能用）；③ 跨文件引用一律写编号，不写标题。

## 2. 字段口径

### 2.1 功能清单字段

| 字段 | 含义 | 填错的典型后果 |
|---|---|---|
| `id` | 功能编号 | 格式不合法 / 重复 → 判定失败 |
| `name` | 一句话功能名 | 空 → 判定失败 |
| `description` | 做什么、边界在哪 | 空 → 判定失败 |
| `status` | 四态之一（未开始 / 进行中 / 已完成 / 被阻塞） | 非法值 → 判定失败 |
| `acceptance` | 验收标准，一条一句，可机械核对 | 空 → 判定失败 |
| `evidence` | 完成的证据（命令 + 结果） | 已完成却为空 → 判定失败 |
| `depends_on` | 依赖的功能编号 | 指向不存在 / 成环 → 判定失败 |

### 2.2 并行相关字段

| 字段 | 在哪 | 含义 | 默认 |
|---|---|---|---|
| 并行上限 | 任务队列 | 同时进行中的功能数量上限 | 1（等价单任务） |
| 认领人 | 认领文件 | 谁在做（人 / 会话 / Agent 标识） | 必填 |
| 范围 | 认领文件 | 我会改哪些路径（可多条，前缀语义） | 建议填 |
| 第几轮 | 认领文件 | 同一认领人的第几轮迭代 | 1 |
| 心跳时长 | 配置 | 多久没心跳算陈旧（只警告） | 12 小时 |

### 2.3 任务页字段

| 字段 | 含义 |
|---|---|
| 状态 | 进行中 / 待验收 / 完成 |
| 最后更新时间 | 页面最后一次变化的时间 |
| 步骤百分比 | 该步骤完成度，0–100 |
| 总进度 | 各步骤等权平均，自动汇总，不手填 |
| 进度记录 | 每一步变化立刻一条：时间 + 变化后的总进度 + 说明 |
| 用例红/绿 | `red` 表示测试先写好还没通过，`green` 表示已通过 |

## 3. 最容易混的六组说法

| 说法 A | 说法 B | 区别（口径） |
|---|---|---|
| 「任务」 | 「功能」 | 功能是**范围**里的条目（做什么）；任务是**一次具体的推进**（一页、一份文档、一份认领）。一个功能可对应多个任务页，但同一时间只应有一个进行中的任务。 |
| 「进度页」 | 「进度日志」 | 进度页是 `prototype/` 下的页面（给人看，含百分比）；进度日志是 `claude-progress.md`（给下一个会话看，含目标 / 已完成 / 下一步）。两者都要更新。 |
| 「规范文档」 | 「任务页」 | 文档在 `docs/specs/`（DDD 设计、SDD 契约、任务规划，稳定、可评审）；任务页在 `prototype/`（状态与百分比，实时变化）。 |
| 「校验」 | 「门禁」 | 校验是一条只读命令（看配置是否合规）；门禁是把 lint + 测试 + 并行上限 + 认领串起来的一条命令（看能不能交付）。 |
| 「完成（done）」 | 「完成（页面）」 | 功能状态 `done` 必须有证据；任务页状态 `完成` 要求全部步骤 100% 且用例全绿。两者不是同一个东西，不要互相替代。 |
| 「认领」 | 「分工」 | 认领是写进仓库的文件（可校验）；口头分工不算。 |

## 4. 日常操作规矩（上手必守）

1. **先认领再开工**（并行时）；没有认领就把功能改「进行中」，校验会失败。
2. **只改自己范围**；跨范围先释放再重新认领。
3. **入口地图不手改**：改配置后重新生成。
4. **状态文件只增量**：进度日志、任务日志、功能清单、任务队列不做整文件替换。
5. **进度不手填总进度**：只改步骤百分比，再追加一条记录。
6. **完成前跑门禁**：不要用「看起来没问题」替代检查结果。
7. **文档与页面同一轮改**：任何一侧改了，另一侧同时改；`docs/specs/<任务>/*.md` 人可以直接改，
   但改完必须重新 `review` 复盘 + `plan --confirm` 确认，否则进度会被拒绝（P22）。
8. **数字口径**：百分比一律整数；时间一律带时区或统一用 UTC；不要出现「约」「差不多」。

## 5. 三处「一处真源」

| 事实 | 唯一真源 | 其他地方只是引用 |
|---|---|---|
| 做什么、验收标准 | 功能清单 | 入口地图、任务页里的链接 |
| 谁在做、改哪些文件 | 认领文件 | 进度日志里的说明（非权威） |
| 进度百分比 | 任务页步骤 | 总览页（汇总结果，不手改） |

## 6. 口径变更怎么走

1. 任何口径变更先改**本页**（或判定规则 + 本页），不要只在聊天里说。
2. 判定与本文冲突时：先确认哪边是错的（以实际行为 + 用例为准），同时修另一边。
3. 变更后重跑一次校验，确认没有引入新的红项。
