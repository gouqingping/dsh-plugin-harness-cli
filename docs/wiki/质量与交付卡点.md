# 质量与交付卡点

> 读者：项目负责人、实施人员。上线前要过哪些检查、谁来负责、**当前哪些检查是失效的**、以及交付时最容易出事的地方。

> **一句话结论：这套系统当前的自动化质量关卡基本处于失效状态，上线前的回归只能依靠人工清单。**

## 1. 关卡全景（规则是真的，触发是缺的）

| 关卡 | 覆盖什么 | 规则是否真实 | **交付前是否会被自动触发** |
|---|---|---|---|
| 自带用例（108 条） | 命令行为、判定规则、模板渲染、平台适配 | 是，全绿 | **否**：仓库不是 git 仓库、没有 CI 运行，只能人工执行 |
| 工具自检（7 项） | 运行环境、模板、渲染、配置、可写、风格引擎、git | 是 | **否**：需人工执行；且只给退出码，不阻断任何流程 |
| 项目校验（A/H/F/V/G/C2xx/P） | 目标仓库的配置与流程证据 | 是，每条规则都有失败用例 | 半自动：只有人主动跑才会执行 |
| 项目门禁（脚本） | lint → 测试 → 并行上限 + 认领 | 是 | 半自动：需要接进入口或流水线；默认没人跑 |
| 代码风格与提交 | 风格、提交信息 | 是（随包引擎） | **否**：提交钩子未安装时不会触发 |
| 生成的 CI 骨架 | 同上 + 项目校验 | 只是**骨架** | **否**：需要客户接入自己的流水线，模板里的凭据与仓库还是占位 |
| 平台集成（6 工具 / 3 命令） | 加载与参数校验 | 部分：仅做过参数模式校验与手工冒烟 | **否**：没有任何自动化回归 |

## 2. 当前哪些检查是「失效」的（逐条说清）

失效 ≠ 规则写错；这里的失效指**没有自动化在交付前触发它**，因此结果不可依赖。

| 编号 | 失效项 | 具体表现 | 后果 |
|---|---|---|---|
| Q-1 | 自带用例无人自动执行 | 仓库无 git、无 CI 配置、无提交钩子 | 改动后可能带着红灯交付 |
| Q-2 | 工具自身不自举 | 对自己的目录跑校验会如实报「缺少四件套」 | 工具自身的配置一致性只能人工判断 |
| Q-3 | 生成的 CI 骨架不会自己跑 | 模板含占位（仓库、凭据、镜像） | 客户以为「接了 CI」，其实没接 |
| Q-4 | 平台集成无回归 | 只有参数模式校验 + 一次手工冒烟 | 平台升级/路径变化时可能静默加载失败 |
| Q-5 | 页面与文档校验靠人触发 | 没有编辑器保存校验、没有提交钩子跑页面校验 | 进度页与文档容易滞后于实际 |
| Q-6 | 环境类检查是软失败 | 缺 python3 → 仅该能力退出码 2；缺 git → 仅警告 | 风格门禁可能被跳过而无人察觉 |
| Q-7 | 心跳超时只警告 | 陈旧认领不会自动清理 | 并行时可能被「僵尸认领」挡住 |
| Q-8 | 没有账号与权限 | 谁能改什么由仓库权限决定 | 「谁改的」只能靠版本库追溯 |

## 4. 交付时最容易出事的 8 个地方

1. **在只读目录里跑**：自检报「不可写」，其实只是目录/沙箱限制；换到目标项目目录即可，别改代码。
2. **没生成骨架就直接校验**：会报一屏「缺少四件套」，被误判成工具坏了。先跑生成命令。
3. **把骨架任务页当成品**：新建任务页必然校验失败（留着「待填」），这是设计；交付前必须填完。
4. **并行上限调大但没人填范围**：认领只校验「填了的范围」；范围空着时无法拦冲突。
5. **平台集成路径失效**：注册项指向的路径（常是符号链接）被移动或删除，平台侧工具静默消失。
6. **缺少 python3**：风格门禁直接失效，且如果流水线里写成「忽略失败」，就永远绿。
7. **状态文件被整文件替换**：进度日志、功能清单、任务队列只能增量维护，被覆盖等于丢历史。
8. **以为生成了 CI 就有人跑**：CI 文件只是骨架，仓库地址、凭据、镜像都要替换，否则不会触发。

## 5. 建议的最小改进（按性价比排序）

| 优先级 | 改进 | 收益 |
|---|---|---|
| P0 | 把仓库纳入版本控制并接入流水线，跑自带用例 + 严格校验 + 门禁 | 让已有的规则真正被触发 |
| P0 | 提交前钩子跑「风格 + 页面 + 校验」 | 把滞后从交付提前到提交 |
| P1 | 平台集成加一条加载冒烟（每次发布执行） | 防止静默加载失败 |
| P1 | 自检结果写入交付记录（时间 + 输出摘要） | 让「跑过」可追溯 |
| P2 | 生成物里把占位（仓库、凭据、镜像）做成显式待办清单 | 避免「以为接好了」 |

> 提醒：以上改进不改变规则本身。规则已经在文件与判定里，缺的是**触发点**。
