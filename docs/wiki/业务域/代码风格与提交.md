# 业务域：代码风格与提交

> 所属域功能点：F6.1–F6.4。上游：无（随包携带判定引擎）。下游：交付验收把它作为一条检查项。

## 1. 能做什么

| 功能点 | 一段话 |
|---|---|
| F6.1 风格检查 | 对暂存区（或指定范围）做代码风格检查，不符合即失败。 |
| F6.2 自动修复 | 能机械修的问题（缩进、引号、导入顺序等）一条命令修掉。 |
| F6.3 提交信息校验 | 提交信息按约定前缀与格式判定。 |
| F6.4 接入提交钩子 | 装一次钩子，之后每次提交自动检查。 |

## 2. 怎么触发

```sh
node <工具>/bin/dsh-plugin-harness-cli.js style doctor              # 依赖与配置自检
node <工具>/bin/dsh-plugin-harness-cli.js style init --lang py,ts   # 给项目接入风格配置
node <工具>/bin/dsh-plugin-harness-cli.js style check --staged      # 0 通过 / 1 违规 / 2 环境问题
node <工具>/bin/dsh-plugin-harness-cli.js style fix --staged
node <工具>/bin/dsh-plugin-harness-cli.js style commit-msg <文件>
```

## 3. 规则

1. **原样透传**：参数不做二次解释，退出码原样返回，方便串进同一条门禁。
2. **先测后修**：先看检查结果，再决定自动修还是手工改；自动修后必须重跑。
3. **需要运行环境**：该能力依赖本机 python3；缺失时退出码 2，其余能力不受影响。
4. **不得绕过**：不允许用「跳过钩子」的方式提交来规避检查。

## 4. 与另一套判定分工

| 工具 | 管什么 | 失败典型原因 |
|---|---|---|
| 项目校验 | 配置与流程证据（四件套、并行上限、认领、证据、链接） | 同时进行中超过上限、完成没证据 |
| 风格与提交 | 代码风格与提交信息（可机械判定的部分） | 缩进、引号、提交前缀不合规 |

两者失败都返回 1，都可以串进同一条门禁：`风格检查 && 项目校验`。

## 5. 失败现象与处理

| 现象 | 含义 | 处理 |
|---|---|---|
| 退出码 1 + 违规列表 | 有风格或提交信息问题 | 自动修能修的，其余手工改，重跑 |
| 退出码 2 | 缺 python3 / 找不到判定引擎 | 先装运行环境或检查安装完整性 |
| 钩子没生效 | 没装钩子或装到了别的仓库 | 重新安装钩子，确认在正确仓库 |
| 修复后仍失败 | 有不能自动修的问题 | 按提示手工改；不要反复跑修复 |
