# 一页纸速览

> 读者：领导、售前、客户。看完这一页能回答三件事：这是什么、值不值得用、边界在哪。
> 全文依据仓库实际文件与判定规则编写，不含推测。

## 1. 一句话

**把「一个项目该怎么被协作」从口头约定，变成能被机器检查的文件。**
输入一句项目说明，输出一整套人和 AI 都能直接照着做的工程配置；改动不合规范就直接失败。

## 2. 它解决什么问题

研发里最常见的四类返工，都不是技术难题，而是「没人写下来 + 没人检查」：

| 现场真实发生的事 | 后果 | 这套系统里的对应物 |
|---|---|---|
| 需求散在聊天记录里，Agent 上手先猜 | 做错方向、返工 | 功能清单（范围 + 验收 + 证据） |
| 换个人/换个会话就接不上活 | 重复调研、进度丢失 | 进度日志 + 任务日志 + 入口地图 |
| 代码风格、提交信息各写各的 | 评审扯皮、合并不了 | 代码风格与提交信息门禁 |
| 「做完了」没有证据，验收靠感觉 | 上线后才发现漏项 | 完成定义 + 证据字段 + 任务页五段 |

## 3. 能力全景（七个业务域）

| 业务域 | 一句话能力 | 谁最常用 |
|---|---|---|
| 初始化与配置 | 一条命令生成项目骨架；入口地图由配置生成，不手写 | 新项目负责人 |
| 校验门禁 | 把规范变成失败：缺文件、缺证据、超并行上限都会红 | 项目负责人、交付 |
| 任务页与进度 | 先方案确认（plan）→ 再页面设计（ui）→ 再推进度（progress）；总进度实时汇总，另有总览页 | 业务、产品、项目负责人 |
| 规范文档 | 每个任务四份文档：提案 / 契约 / 设计 / 任务规划 | 产品、开发 |
| 并行认领 | 多会话同时推进时，谁做什么、改哪些文件写在仓库里 | 多 Agent / 多人协作 |
| 代码风格与提交 | 风格与提交信息按同一套规则判定，可自动修复 | 开发 |
| 自检与集成 | 工具自检；装进 DSH 后成为模型可直接调用的工具（含业务 wiki 生成） | 平台、交付 |

## 4. 业务价值

- **交接成本**：新会话 / 新同事只读仓库文件就能恢复现场，不依赖谁记得。
- **返工成本**：范围、验收、证据都在文件里，「做完了」必须能说清怎么验的。
- **协作成本**：并行时先认领、只改自己范围，冲突在开工前就被拒绝，而不是合并时才发现。
- **交付风险**：上线前有一条可重复执行的检查链（自检 → 校验 → 门禁 → 场景验收）。
- **AI 可控**：规则落在文件与判定里，不依赖提示词写得好不好。

## 5. 典型场景

1. **新项目起步**：生成骨架，填配置，跑一次校验，团队就有了统一入口。
2. **老项目补规范**：只补缺失项，不覆盖已有内容，状态文件永不覆盖。
3. **多会话并行**：调大并行上限，各自认领任务，范围不重叠。
4. **交付前验收**：自检 → 校验 → 门禁 → 按场景过验收清单。

## 6. 边界（明确不做什么）

- **不是项目管理软件**：没有账号、看板、甘特图；它只产出文件，进度看页面。
- **不是代码生成器**：不写业务代码，只生成「怎么协作、怎么验收」的配置与文档骨架。
- **不是代码托管/CI 服务**：不联网、不执行远程流水线；生成的 CI 骨架需要接进客户自己的流水线。
- **不替代评审**：规则只管机械可判定部分（有没有、对不对、一致不一致），需求好坏仍要人判断。
- **不做权限与合规**：没有登录、审计、加密存储；数据就是仓库里的文本文件。

## 7. 交付与验收要点

| 环节 | 要点 |
|---|---|
| 环境 | 目标机器有 Node.js ≥ 18；代码风格能力另需 python3 ≥ 3.8 |
| 安装 | 三种形态任选：源码直接运行 / 装进 DSH / 整个插件目录拷走 |
| 数据 | 全部落在目标仓库文件里，无数据库、无服务、无外网 |
| 验收 | 生成物齐备 → 校验通过 → 门禁全绿 → 按场景清单逐条确认 |
| 回滚 | 删掉生成的目录与配置、或按备份还原注册文件即可，不残留服务 |
