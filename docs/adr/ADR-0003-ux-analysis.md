# ADR-0003：UX 与需求分析（`ux`）用全项目报告 + 维度优先级 + 缺口生命周期

- 状态：已接受
- 日期：2026-11-12
- 相关：ADR-0001、`prototype/ux.html`、`plugin/src/ux.js`

## 1. 背景

任务文档（proposal / spec / design / flow）与 UI 说明里已经写了不少业务事实，但要回答
「用户是谁、场景是什么、需求拆成几条、体验哪里会断」仍要人工从头读一遍。直接让模型自由发挥，
结论不可复核，也容易把推断当成事实写进仓库。

第一版 `ux` 以「本次选中的任务 / 自定义需求」为范围，实际使用暴露了三个问题：

1. **整体报告会随每次选择缩水**：只选一个任务时，`prototype/ux.html` 就只剩这个任务，
   无法回答「项目整体怎么样」；
2. **待确认清单只增不减**：条目没有稳定编号，也没有「已确认」的落点；人一条条补完后，
   清单看起来仍在，无法判断还剩多少；
3. **任务之间的关联被忽略**：一个任务的需求 / 术语 / 流程变了，关联任务没有同步刷新，
   两边口径会漂移。

## 2. 决策

改造 `ux` 子命令与 `harness_cli_ux` 工具：

- **全项目口径**：`prototype/ux.html` 永远分析仓库里的全部任务；命令里的任务参数只决定
  `--apply` 回写谁（单任务报告每次都会刷新）。没有任务参数也能直接跑（仓库里没有任务、也没有项目需求时才报用法）。
- **项目需求持久化**：`--user-words` 追加到 `docs/ux/requirements.md` 的受管区块；后续重跑即使不传
  需求，整体报告也会带上，不会因为某次运行丢掉上下文。
- **维度优先级**：报告按 用户与场景 → 需求拆解 → 任务关联 → 体验流程 → 异常与恢复 → 状态与反馈 →
  可用性 → 文档完整性 组织；每个维度先给分析结论，再列缺口。用户 / 场景 / 需求 / 流程 / 异常缺的
  事实不再只写成表格里的「待确认」，而是进入同一份待确认清单。
- **缺口生命周期**：缺口编号由「任务 + 维度 + 描述」哈希得到，重跑保持稳定。每次重跑按文档重算：
  文档修好，缺口自动消失；`ux --resolve <编号> --by "确认人"` 逐条关闭，写入
  `prototype/.ux-resolved.json`，报告只列未关闭项并折叠已关闭项；文档修好后关闭记录一并清理，
  避免文档回退时被误关。
- **任务关联与同步**：任务文档里写「关联任务：任务名」即显式关联，文档里互相提及也会识别为
  「文档提及」。`--apply` 在回写选中任务时，顺带刷新直接关联任务的 UX 复核区块；关联任务之间
  术语定义不一致会进入待确认。DSH 更新提示也会要求 Agent 一起核对关联任务。
- **DSH 侧流程**：报告完成后询问「更新任务 / 逐条关闭待确认项 / 创建新任务 / 仅保留报告」；
  阻断缺口先派发「按维度逐条补 → 重跑 ux」，清单会随补全自动缩短。
- **输出**：`prototype/ux.html`、`prototype/ux.json`、`prototype/.ux-gaps.json`、
  `prototype/.ux-resolved.json`；每个任务 `prototype/<任务>/ux/index.html` + `report.json` + `.ux-gaps.json`。

## 3. 后果

- 正面：整体报告不再随单次选择变化，可以直接回答「项目整体 UX 与需求」。
- 正面：缺口有编号、可关闭、会自动清理，分析完成度可以度量，不再只有「待确认」四个字。
- 正面：任务关联显式化，`--apply` 默认同步直接关联任务，减少跨任务口径漂移。
- 负面：整体报告每次都读全部任务，任务很多时生成时间会随任务数增长（仍是本地文件读取）。
- 负面：`docs/ux/requirements.md` 与 `prototype/.ux-resolved.json` 是新增状态文件，需要随仓库提交；
  删除它们会让项目需求 / 已确认记录丢失。
- 负面：任务关联靠显式声明与文本提及推断，可能漏掉隐含关联；需要更严格时应在文档里写清楚
  「关联任务：…」。
- 负面：`prototype/ux.html` 与 `prototype/<任务>/ux/index.html` 是生成物，人工改动会在重跑时被覆盖；
  要长期保留的结论写回 `docs/specs/<任务>/`。

## 4. 被否决的方案

- **保留「本次范围」作为整体报告**：无法回答项目整体问题，与「整体报告」的名字不符。
- **只靠自动重算，不提供逐条关闭**：文档无法自动证明的事项（外部依赖、口头确认）永远留在清单里，
  无法区分「还没做」和「已经确认」。
- **让模型直接写报告、工具只负责弹窗**：结论不可复核，重跑不可重复，也无法判断「分析完成」。
- **把 UX 分析塞进 `wiki`**：wiki 面向业务文档，报告需要任务 / 项目需求两种入口与更新 / 关闭 / 创建决策，
  职责不同。
- **分析后直接改任务文档**：未经用户确认就改设计文档，违背「不覆盖人工内容」的约束；
  因此拆成报告 → 询问 → `--apply` 两步。
- **把关联任务的全部文档一起自动改写**：工具只同步受管区块，业务内容仍由 Agent / 人按报告更新，
  避免自动生成第二份事实。

## 5. 验收方式

- `node --test` 全绿，含 `plugin/tests/ux.test.js` 的全项目覆盖、项目需求持久化、缺口编号与关闭、
  维度优先级、关联任务同步用例，以及 cordis 的整体报告、逐条关闭、工具参数用例；
- 仓库里有多个任务时，只传一个任务，`prototype/ux.html` 仍包含全部任务（e2e 覆盖）；
- 骨架任务：用户 / 场景 / 需求 / 流程 / 异常缺口都进入待确认，且按维度优先级排序；
- 关闭一条缺口后重跑，报告与 `.ux-gaps.json` 中不再出现；把文档补好后重跑，缺口消失且关闭记录被清理；
- 显式关联两个任务后 `ux --apply <任务甲>`，任务乙的 `design.md` UX 区块也被刷新；
- 报告 HTML 不出现模板残留、不执行用户输入（文本已转义）。
